# 平台机制设计总纲

> 项目：制造业产能编排与竞标平台（大批量、长周期、多工序、强质检场景）
> 定位：需求方与工厂之间的「绝对公正法典 + 可信长期合作平台」
> 设计总原则：**安全第一、稳定第二、精简第三、功能第四**

---

## 0. 战略定位与设计哲学

### 0.1 定位声明

> 不做「更好的 Xometry / 海智在线」（需求侧、小批量快速件、轻资产、压榨供应商的订单分发商）；
> 做「大批量复杂制造订单的 AI 产能编排 + 独立第三方质检 + 供给侧共赢」平台。

### 0.2 平台的角色哲学（出淤泥而不染）

平台**不碰判定权、只碰流程权**，是「规则制定者 + 信息中介 + 资金托管 + 存证仲裁者」，而不是「交易当事人」：

| 平台做 | 平台坚决不做 |
|---|---|
| 制定规则、维护状态机 | 不碰质检判定（交给第三方机构） |
| 资金托管、按节点放款 | 不碰货、不碰生产 |
| 存证、留档、仲裁依据 | 不替任何一方做质量/交期背书 |
| AI 编排推荐（只推荐、不强制） | 不当「运动员」，不赚买卖差价 |
| 信用评分与公示 | 不泄露双边敏感信息 |

> 核心原则：**平台的中立性是唯一不可消耗的资产。** 任何短期套利行为（赚差价、偏袒一方、截留资金）都会摧毁平台的长期公信力。

### 0.3 设计优先级（本项目技术成败的第一性原则）

```
安全性（含支付/用户信息） > 平台稳定性 > 网站逻辑精简性 > 功能丰富度
```

任何功能若与安全、稳定、精简冲突，**一律砍功能保前三项**。本总纲后文按此优先级组织。

## 1. 角色与权责模型

| 角色 | 权力 | 义务 | 红线（不能做） |
|---|---|---|---|
| **需求方（买家）** | 发起需求、选定方案、验收、发起复检/仲裁 | 交诚意金、如实提交需求与预算/交期权重、按节点付款 | 白嫖报价、虚假需求、绕过平台交易、恶意压价 |
| **工厂方（供给侧）** | 报价、竞标、展示能力、申诉 | 交保证金、如实提交产能日历与工期承诺、按承诺交付 | 过度承诺、偷工减料、跳单、串标围标 |
| **第三方质检机构** | 独立抽样、出具报告 | 对报告真实性负法律责任、报告上链留档 | 与交易任一方利益勾连 |
| **平台运营方** | 制定规则、托管资金、存证、仲裁、AI 推荐 | 中立、保密、信息披露、反欺诈 | 碰判定权、赚差价、挪用托管资金、泄露双边数据 |
| **金融机构（可选）** | 提供供应链金融、账期垫资 | 合规、风控 | 与平台串通挪用资金 |

> 多租户数据隔离是硬约束：每一方只能看到**自己被授权看到的数据**，跨租户数据物理/逻辑隔离，详见第 7 章。

## 2. 核心机制设计（双边对称机制）

### 2.1 双边对称原则

买家与工厂必须接受**同一套「诚意 + 信用 + 托管 + 留档」逻辑**，谁都不被偏袒，谁都不能耍赖：

| 博弈痛点 | 买家侧机制 | 工厂侧机制 |
|---|---|---|
| 白嫖 / 流拍 | 买家诚意金 + 托管定金 | 竞拍保证金（按阶段释放） |
| 变卦 / 过度承诺 | 变更保证金 + 需求锁版 | 里程碑违约金 + 产能日历验证 |
| 信息藏私 | 多方案菜单暴露预算/交期权重 | 报价强制含工期曲线 + 良率 + 占用产能 |
| 信用 / 能力 | 买家信用分 + 历史付款记录 | 工厂信用分 + 履约记录 + 能力证书 |
| 跳单 / 绕平台 | 匿名询价 + 平台代谈判 | 供应商隐藏 + 资金全托管 |
| 挤兑 / 塌方 | —— | 价格地板 + 订单预测 + 供应链金融 |

### 2.2 多维报价模型（解决「平台不懂工厂」）

工厂报价不是一个数字，而是多维向量：

```
报价 = {
  价格(总价/单价),
  分阶段工期曲线[阶段1交X件@D1, 阶段2交Y件@D2, ...],   // 由工厂自己承诺，不是平台拍脑袋
  各阶段良率承诺,
  占用产能(设备×时段),
  质量认证与能力证明,
  附加条件(最小起订、材料锁价条款等)
}
```

> 设计动机：平台不规定「四阶段」，而是让工厂在报价里**自己提交分阶段工期**。因工厂彼此竞标博弈，会自我压迫出真实能力承诺。

### 2.3 评选机制（防「赢者诅咒」）

**核心矛盾**：竞标压力会逼出「承诺的最优解」，但赢家往往是「最乐观/最敢吹」的厂（赢者诅咒），而非「最能干」的厂。

**四道护栏，把「自压迫」从结果降级为输入：**

1. **里程碑绑定的保证金释放**——保证金不一次性收，而是按阶段释放：准时交第1阶段退一部分，延期按天扣，让「过度承诺」变贵。
2. **产能日历验证**——报价时必须提交实时产能日历，平台核对「承诺工期 vs 空闲产能」是否撑得住，直接剔除明显不可行的激进报价。
3. **信用分折扣**——首次合作、无履约记录的厂，评分打折；历史准时率高的厂获得溢价权。让「吹牛」有长期代价。
4. **中间品检验节点**——多工序交接处设硬检验，双方责任划清，缓冲期写进工期。

### 2.4 评分函数（买家权重可选）

```
综合评分 = w1·(成本分) + w2·(工期分) + w3·(质量/良率分) + w4·(信用分)
           - 惩罚项(激进承诺折扣) - 惩罚项(产能日历不匹配)
```

买家在发单时选择权重（成本优先 / 工期优先 / 质量优先），**菜单选择本身暴露买家的真实偏好**——这就是「逼买家说真话」的机制。

### 2.5 AI 编排（决策层）

竞标产出的是**单点承诺**，AI 负责把它们拼成**链条最优**：

```
输入：所有工厂的多维报价 + 产能日历 + 工序依赖(m粗→n精→...→组装)
输出：A/B/C 多方案
      A = 成本最优（组合上各工序取最低价，接受较长工期）
      B = 平衡
      C = 工期/质量最优（高价、短周期、高良率）
约束：工序依赖、中间品缓冲、责任划分、帕累托最优
```

> 「自压迫竞标」生成原料，「AI 编排」组装成真正最优链条。缺前者 AI 没数据，缺后者自压迫只是一堆互相打架的空头承诺。

### 2.6 分阶段交付与里程碑资金释放

```
阶段0 合同签订    → 双方诚意金冻结
阶段1 交付X1件    → 第三方质检 → 合格 → 释放保证金A% + 放款A%
阶段2 交付X2件    → 第三方质检 → 合格 → 释放保证金B% + 放款B%
...
阶段N 终检交付    → 全部合格 → 释放尾款 + 全部保证金
```

资金释放**严格绑定质检合格结果**，平台不碰判定、只执行规则。

### 2.7 佣金机制（收入模型）

#### 2.7.1 核心定位

佣金是平台的**基本盘 + 防跳单的象征价**，不是主要利润池（主要利润池后续为供应链金融与按效果分成，本期不做）。

> 核心原则：**佣金费率是「信用资产」，必须恒定、透明、不可谈判；能「自定义」的只有「谁承担」和「各工厂分摊比例」，绝不是「费率本身」。**

#### 2.7.2 计费规则

| 项 | 规则 |
|---|---|
| 费率 | 平台统一锁定，区间 **0.5%~1%**，公开、恒定、不可谈判，全平台一致 |
| 计费基数 | 按**订单总成交额（可承接订单总额）一次计算**，不按各工位分别重复计费 |
| 分摊 | 多工厂按各自成交额占比**透明分摊**，单家实际负担在竞标时即清晰可见 |
| 展示 | 工厂竞标时，每个工位/工序位子明示：该位子成交后平台抽佣比例 + 实际需负担佣金（动态估算） |
| 内化 | 佣金负担内化为工厂报价的一部分，工厂报价时已含该成本，杜绝事后震惊 |
| 承担方 | 可协商由买家/工厂分担，但**总费额不变**，不影响平台收入 |

#### 2.7.3 铁律（禁止项）

- ❌ 佣金费率不得作为竞标筹码（禁止「低佣金换中标」或「高佣金买结果」）。
- ❌ 平台不得赚买卖差价、不得与成交价正相关套利（否则中立性崩）。
- ❌ 不得按各工位重复计费、不得模糊佣金口径（统一按订单总额一次计，占比分摊）。
- ❌ 任何一方不得通过提高/降低佣金换取中标优势。

#### 2.7.4 多工厂分担的结构红利

大单多工序分包模式下，佣金总额由 N 家工厂分摊，单家实际负担远低于「一单一厂」撮合模式：

```
一单一厂：7000 万订单 × 1% = 70 万，全压 1 家（痛感高 → 易跳单）
多工序分包：7000 万订单 → m粗+n精+表面+组装 共 4 家
            → 佣金总额仍 70 万，按占比分摊，单家可能仅 0.2%~0.3%
```

**结论**：同样的平台收入，分摊到每家工厂的痛感只剩 1/N，这是大单模式独有的「跳单免疫」红利——跳单省下的佣金，远小于留在平台获得的担保、质检、垫资、信用溢价的代价。

#### 2.7.5 本期明确不做

- 增值服务（加急质检、专属编排、延长账期、优先派单、信用报告等）**本期全部不做**，聚焦把主业务流程做到极致。
- 供应链金融、按效果分成等利润层**本期不做**，留待主流程验证后再开。

## 3. 详细功能设计

### 3.1 需求方（买家）模块

- **需求发布**：结构化向导（图纸/公差/材料/AQL/认证/数量/交期/是否多工序），填不满不能发单（过滤钓鱼需求）。
- **双字段交期**：硬交期 vs 弹性交期分开填，弹性交期换取低价。
- **权重菜单**：成本/工期/质量权重选择（暴露真实偏好）。
- **方案比选**：查看 A/B/C 方案，横向对比总价、总工期、各阶段、质检安排、责任条款。
- **合同与锁版**：在线签约、需求版本锁定、变更走流程并收费。
- **付款**：资金托管、分阶段付款、发票管理。
- **验收/复检/仲裁**：发起复检、申请换质检机构、申请平台仲裁。

### 3.2 工厂方（供给侧）模块

- **能力档案**：设备清单（型号/精度/加工能力）、可加工材料、工艺能力、历史合格率、认证证书。
- **产能日历**：实时维护空闲产能（设备×时段），作为竞标硬约束。
- **多维报价**：提交价格 + 分阶段工期曲线 + 良率 + 占用产能。
- **竞标参与**：匿名参与、查看自己是否入围、接收中标/落选通知（不泄露竞对信息）。
- **履约管理**：生产进度上报、报工、中间品流转交接。
- **资金与信用**：查收款节点、查信用分变化、申请供应链金融。

### 3.3 平台运营模块

- **规则引擎**：保证金比例、违约金、价格地板、评分权重等可配置。
- **状态机看板**：全量订单/竞标/工单/质检/资金的状态监控。
- **反欺诈**：串标围标识别、异常报价识别、设备/企业真实性核验。
- **信用体系**：双边信用分计算、公示、申诉。
- **仲裁中心**：存证调阅、规则解释、仲裁结论留档。
- **审计中心**：全链路操作审计、资金审计、合规报表。

### 3.4 第三方质检模块

- **机构准入**：资质核验、利益冲突审查、年度复核。
- **抽样方案**：抽样方案在合同中锁死（各阶段抽多少、AQL、判定规则、费用承担）。
- **报告生成与上链**：报告哈希上链，不可篡改，作为仲裁证据。
- **复检机制**：买家对报告有异议可申请复检/换机构，费用由败诉方承担。

### 3.5 资金与支付模块（详见第 8 章）

- 资金托管、保证金管理、分阶段放款、退款/违约金、对账、供应链金融。

### 3.6 多工序编排模块

- 工序依赖图维护、m/n 组合枚举、中间品检验节点、缓冲期设置、全局工期/成本优化。

## 4. 详细流程设计（状态机驱动）

> 本项目所有核心流程**必须显式建模为状态机**，状态迁移是唯一合法路径，任何非法迁移被系统拒绝。这是「网站逻辑精简性」的根本手段（详见第 9 章）。

### 4.1 主流程状态机

```
需求方                     平台                      工厂                第三方质检
  │                          │                          │
  ├─ 发布需求(锁版) ────────►│                          │
  │   + 诚意金冻结           │                          │
  │                          ├─ 需求审核/反欺诈 ────────►│
  │                          │   (资质过滤)             │
  │                          ├─ 发起竞标 ──────────────►│ 报价(多维+保证金冻结)
  │                          │◄─────────────────────────┤
  │                          ├─ AI 生成 A/B/C 方案       │
  │◄─ 选方案 ────────────────┤                          │
  │   (暴露偏好)             │                          │
  │                          ├─ 中标确认 + 合同签订       │
  │                          │   (双方保证金冻结)        │
  │                          ├─ 阶段1 下达 ─────────────►│ 生产+报工
  │                          │◄─ 阶段1 交付 ─────────────┤
  │                          ├─ 第三方质检 ────────────────────────────►│ 抽样+报告上链
  │                          │◄──────────────────────────────────────────┤
  │                          ├─ 合格 → 释放保证金+放款 ─►│
  │                          │   (不合格 → 返工/报废/违约金)
  │                          ├─ 阶段2 ... 阶段N          │
  │                          ├─ 终检 + 整体验收 ────────►│
  │◄─ 验收确认 ──────────────┤                          │
  │                          ├─ 释放尾款 + 全部保证金 ───►│
  │                          ├─ 信用分结算 + 评价         │
```

### 4.2 订单生命周期状态

```
草稿 → 已发布 → 竞标中 → 方案已生成 → 方案已选定 → 合同已签订
  → 生产中(阶段1..N) → 质检中 → 已交付 → 已验收 → 已完成
  → 异常态：已取消 / 已延期 / 已违约 / 纠纷中 / 仲裁中 / 已关闭
```

### 4.3 异常流程（必须有，缺了必死）

| 异常场景 | 处理规则 |
|---|---|
| 需求取消 | 已冻结诚意金按阶段成本比例扣；未产生成本的退款 |
| 竞标流拍 | 退还工厂保证金；买家诚意金按约定部分退（防白嫖） |
| 工厂延期 | 按天扣保证金/违约金；触发信用分下调；必要时启动替补工厂 |
| 质检不合格 | 返工（工厂承担）或报废+违约金；触发信用分下调；费用责任按合同 |
| 买家中途变更（ECO） | 需求锁版被打破 → 收取变更费 + 变更保证金，重新评估工期成本 |
| 买家违约拒付 | 保证金+托管资金按合同赔付工厂；买家信用分大幅下调 |
| 中间品交接扯皮 | 中间品检验节点报告作为唯一判定依据，责任按合同划分 |
| 双方纠纷 | 平台仲裁（依据合同 + 区块链存证），仲裁结论留档可追溯 |
| 第三方机构失职 | 报告作废、更换机构、机构承担法律责任、移出准入名单 |

## 5. 技术框架（整体架构）

### 5.1 分层架构

```
┌─────────────────────────────────────────────────────────┐
│  接入层：Web(GUI) / 移动端 / 工厂端 / 开放 API / 第三方   │
├─────────────────────────────────────────────────────────┤
│  网关层：API Gateway（认证/限流/路由/审计/防重放）         │
├─────────────────────────────────────────────────────────┤
│  应用层（微服务，按领域拆分）                              │
│   用户/企业/租户 │ 需求/订单 │ 竞标/报价 │ 方案/编排(AI)    │
│   合同 │ 工单/阶段 │ 质检 │ 信用 │ 资金/支付 │ 存证/仲裁    │
├─────────────────────────────────────────────────────────┤
│  领域层：状态机引擎 / 规则引擎 / 评分引擎 / 编排引擎        │
├─────────────────────────────────────────────────────────┤
│  基础层：消息队列 │ 缓存 │ 分布式事务 │ 任务调度 │ 监控告警  │
├─────────────────────────────────────────────────────────┤
│  数据层：业务库(MySQL) │ 账务库 │ 文档/对象存储 │ 区块链存证  │
│         │ 缓存(Redis) │ 搜索引擎 │ 数仓/报表 │ 密钥管理(KMS) │
└─────────────────────────────────────────────────────────┘
```

### 5.2 技术选型（建议）

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | Java 17 + Spring Boot 3 / Spring Cloud | 生态成熟、账务类业务稳 |
| 前端 | Vue 3 + TypeScript + Element Plus | 与需求文档技术栈一致 |
| 数据交互 | Axios + 网关 | 前后端分离 |
| 业务库 | MySQL（分库分表/主从） | 事务强一致 |
| 账务库 | 独立数据库 + 账务模型（复式记账） | 资金安全前提 |
| 缓存 | Redis Cluster | 分布式锁、限流、幂等 |
| 消息 | Kafka / RocketMQ | 削峰、异步、事件溯源 |
| 编排算法 | 运筹优化求解器（OR-Tools/自研启发式）+ Python 服务 | AI 编排 |
| 存证 | 区块链（联盟链，如 FISCO BCOS）/ 可信时间戳 | 质检报告、合同、流水上链 |
| 支付 | 持牌第三方支付 + 银行资金存管 | 平台不碰资金池（详见第8章） |
| 密钥 | KMS / 硬件安全模块(HSM) | 支付与加密密钥托管 |
| 监控 | Prometheus + Grafana + 链路追踪 | 稳定性 |
| 部署 | K8s + 容器化 + 多可用区 | 高可用 |

### 5.3 关键架构决策

1. **资金与业务分离**：账务库独立部署，资金操作走专用服务 + 复式记账，任何业务模块不得直接读写资金。
2. **状态机外置**：流程状态由独立状态机引擎统一管理，避免状态散落在各微服务。
3. **幂等优先**：所有资金、下单、支付、质检判定接口**强制幂等**（唯一业务号 + 幂等表）。
4. **事件驱动**：关键业务事件（下单、支付、质检合格、放款）走消息队列，保证可追溯与最终一致。
5. **多租户隔离**：数据表带 `tenant_id` + 行级权限，敏感字段加密存储。

## 7. 安全性设计（最高优先级之一）

### 7.1 应用安全

| 威胁 | 对策 |
|---|---|
| 未授权访问 | OAuth2 / JWT + RBAC + 多租户行级权限 |
| 越权（IDOR） | 所有接口校验 `tenant_id` + 资源归属，服务端强制鉴权 |
| SQL 注入 | MyBatis 参数化查询 + 输入白名单校验 |
| XSS | 输出编码 + CSP 头 + 前端框架默认转义 |
| CSRF | CSRF Token + SameSite Cookie |
| 重放攻击 | 请求签名 + 时间戳 + nonce + 防重放表 |
| 暴力破解 | 登录限流 + 验证码 + 账号锁定 |
| 文件上传 | 类型/大小/内容校验 + 独立域名 + 病毒扫描 |
| 依赖漏洞 | 供应链扫描 + 依赖白名单 + 定期升级 |
| 接口滥用 | 网关限流 + IP/账号维度风控 |

### 7.2 数据安全

- **传输加密**：全链路 TLS 1.2+。
- **存储加密**：敏感字段（手机、身份证、报价底价、账务）AES-256 加密，密钥走 KMS/HSM。
- **脱敏**：展示层按角色脱敏（工厂互相看不到彼此报价、买家看不到工厂身份等）。
- **备份**：数据库每日全量 + 实时增量，跨地域备份，定期恢复演练。
- **审计**：全量操作审计，关键操作（资金、质检判定、合同）上链存证。
- **最小化收集**：遵守《个人信息保护法》《数据安全法》，只收必要信息，提供删除/导出权。

## 8. 支付安全性设计（重中之重）

### 8.1 资金架构铁律

> **平台绝不碰资金池。** 平台只做「托管指令 + 节点释放规则」，资金实际存放在**持牌第三方支付机构 / 银行存管账户**。

```
买家 ──资金──► 银行存管账户(托管) ──按规则放款──► 工厂
平台 ──只发指令，不经手资金──► 存管系统
```

### 8.2 资金安全控制点

| 控制点 | 做法 |
|---|---|
| 资金托管 | 银行存管/持牌支付机构，平台账户与用户资金物理隔离 |
| 账务模型 | 复式记账（借贷平衡），账务库独立，任何操作可对账 |
| 幂等 | 支付/放款/退款接口强制幂等，防重复扣款/重复放款 |
| 签名验签 | 与支付机构通信双向签名 + 验签，防篡改 |
| 回调安全 | 支付回调验签 + 幂等 + 状态机校验，防伪回调 |
| 金额防篡改 | 订单金额在服务端重算，不信任前端传入金额 |
| 风控 | 大额交易人工复核、异常流水实时风控、冻结/止付能力 |
| 对账 | 每日与支付机构对账，差异自动告警 + 人工处置 |
| 合规 | 持牌经营、反洗钱(AML)、客户身份识别(KYC) |
| 审计 | 资金操作全程留痕 + 上链，可追溯至每一分钱 |

### 8.3 分阶段资金释放规则（与质检绑定）

```
冻结双方诚意金/保证金
  → 阶段1质检合格 → 释放保证金A% + 向工厂放款A%
  → 阶段2质检合格 → 释放保证金B% + 向工厂放款B%
  ...
  → 终检验收合格 → 释放尾款 + 全部保证金
  → 异常(延期/不合格/违约) → 按合同扣保证金/违约金 → 信用分下调
```

> 资金释放**只能由「质检合格」状态迁移触发**，由状态机引擎统一执行，任何人工或业务代码不得直接改资金。

### 10.1 高可用

## 11. 网站逻辑精简性设计（最高优先级之一）

> 平台的业务天然复杂（竞标、多工序、质检、资金、信用），**复杂是敌人**。精简性的本质是：**让复杂只存在于被显式管理的地方，而不是散落在代码里。**

### 11.1 五个精简原则

1. **状态机收敛一切流程**：所有单据的生命周期由一个显式状态机引擎管理，状态迁移是唯一合法路径，代码里不散落 if/else 状态判断。
2. **领域单一职责**：每个微服务只负责一个聚合根，服务间只通过事件通信，不共享数据库。
3. **幂等优先**：所有写操作天然幂等，前端可安全重试，减少「重复下单/重复放款」类 Bug。
4. **接口最小化 + 错误码唯一化**：接口数量克制，每个接口单一职责；全平台统一错误码，前端统一处理。
5. **配置化而非硬编码**：保证金比例、违约金、评分权重、价格地板等**业务规则配置化**，改规则不改代码。

### 11.2 反模式（明确禁止）

- ❌ 跨服务直接读对方数据库
- ❌ 在业务代码里散落状态判断（必须走状态机）
- ❌ 资金、支付逻辑写在业务模块里（必须走资金服务）
- ❌ 前端信任传入的金额、权限、状态
- ❌ 同一业务逻辑在多处重复实现

## 13. 一句话总结

> 本平台成败不在功能多少，而在**能否守住中立、安全、稳定、精简四条底线**：平台不当裁判只守规则、资金不过手只托管、流程不散落只走状态机、复杂不外溢只收敛。守住这四条，平台才能真正「出淤泥而不染」，成为双边长期信赖的公正法典。
